# Auto-fix (watching the PR)

Read this when: a run watching its ready PR (after `mark_ready`, a triage or steps fix run after its push, or a conflict resolution). It adds to `.claude/agents/orchestrator.md`; where the two differ, this guide wins for the run.

After `mark_ready` succeeds (unattended), your run is `watching`. Slopmux does not fail a quiet watcher for being idle, but it does fail one that ignores failed checks: if the PR head's checks fail (not inherited from the base) and you make no slopmux call or push within the board's response window (default 30 minutes), the run ends with "Auto-fix didn't respond to failed checks". So:

1. **Subscribe.** Call `subscribe_pr_activity` (`mcp__claude-code-remote__subscribe_pr_activity`; load it with ToolSearch if it isn't listed) for the glob's PR (`get_glob` gives `pr.number`; the repository is the board's repo) right after `mark_ready`. Check events arrive as `<wake reason="external-event">` messages. If the tool is not available, call `report_failure` with that reason: a watcher that can't hear about failed checks is useless.
2. **Look at what is already there: right after subscribing, and again before ending any turn while watching.** An event only reports what happens after you subscribe, so checks that finished earlier (often in the same second as `mark_ready`) never wake you. Call `get_glob` (or `check_run`) with your run ID and read `headChecks` for the current `pr.headSha`, and read the PR's comments with the GitHub tools. Checks `failed` on this glob's own change (no `inheritedFrom`): fix them now, as in step 4. `pending`: check again after a short wait with the tools you have (never a sleep loop in Bash), at most 3 times, then end the turn: a later completion arrives as an event. Review comments already on the PR that nobody has addressed: handle them as you would one that arrives as an event. Never end a turn while watching with a known failed head unfixed.
3. **On every event, call `check_run` with your run ID first.** That records progress and shows the state: stop if `current` is false, an `implementer` is recorded, or the glob is `merged`. `headChecks` says whether the head's checks passed, are pending or failed, with the head's SHA; when they failed, call `get_glob` for the failing check, its step and the first error lines (`failedChecks`). `headChecks.inheritedFrom` means the base is red (see "A red base branch is not yours to fix").
4. **Failed checks of this glob:** reproduce the failing check's command locally, fix the cause, run the fast checks, apply the pre-push check, commit with the `Slop-Run` trailer and push. Then wait for the next event. Never skip, disable or quarantine a test to get green.
5. **Anything else** (passed, pending, a comment you can't act on): after the look in step 2, do nothing and end your turn; an idle watcher on a healthy PR has no timeout. A merged or closed PR ends the watch.
6. If you cannot fix the failure, call `report_failure` rather than going quiet.

A run started by **Retry auto-fix** is a watcher from the start: the PR is already ready, so skip the phases and `mark_ready`, call `get_glob` (with the run ID), subscribe as in step 1, look as in step 2 and fix the failed checks as in step 4. There are no board transitions to make: slopmux learns about pushes, the ready PR and the merge from GitHub.

- **A red base branch is not yours to fix.** When the PR's checks fail (auto-fix), call `check_run` first. If `headChecks.inheritedFrom` is set (`get_glob`'s `failedChecks.inherited` is true), the base fails the same way: do not patch its error here and do not push (a second fix collides with the base owner's). Record the failing check, its first error and the glob in `inheritedFrom.since` in an `Assumptions` attachment. Slopmux brings the branch up to date and re-runs the checks when the base goes green; if they still fail with `inheritedFrom` unset, the failure is this glob's.
